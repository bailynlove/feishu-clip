# Bridge web clip job protocol

`PersistentJobStore` is the MVP seam between the localhost Bridge transport and the clip worker. It persists one record per **clip attempt** in an atomically replaced JSON file.

## Identity and idempotency

- The extension generates a fresh `attemptId` for every deliberate click.
- HTTP retries, popup reconnects and worker retries reuse that `attemptId`.
- Reusing an `attemptId` returns the existing job; reusing the same source URL with a new `attemptId` creates a new job.
- The Bridge is single-process. The store serialises mutations within that process; it is not a multi-process database.

## Worker lease and popup recovery

- `claim` moves `queued → running` and assigns a time-limited worker lease.
- `heartbeat` extends a lease only for its active worker. The executor heartbeats periodically (default every 15s, `heartbeatMs`) for the whole duration of an execution (#89), because stages like the AI digest routinely outlast the 60s lease; if a heartbeat fails the worker treats its lease as lost and aborts without further writes (`LEASE_LOST`), letting the requeued successor take over.
- The executor drains two lanes in parallel (#91): `clip` jobs serially among themselves (wiki create must not race), `pdf` jobs on their own lane so a Drive upload never waits behind a clip's digest.
- `recoverExpired` requeues a running job whose lease expired, preserving its `step` and incrementing `retryCount`.
- The popup keeps the `attemptId` in extension storage and restores UI state with `get` or filtered `list` calls after reopening.
- Statuses, steps, failure stages and cleanup outcomes use exported constants and reject unsupported values at public boundaries.

## Ambiguous create timeout

Before calling Feishu, the worker must persist `beginCreate`. A crash with this barrier active recovers into `reconciling`, never directly into another create call. An explicit timeout then uses `markCreateAmbiguous`, which also moves the job to `reconciling`. Neither lease recovery nor a new worker may retry document creation from that state. The Bridge must first query the target Wiki using its attempt marker:

- document found → `resolveAmbiguousCreate` records it and queues `write_body`;
- confirmed absent → it queues `create_document` again;
- reconciliation itself expires → `needs_attention`.

This query runs in the Bridge's sweep (`ClipExecutor.reconcile()`): once at startup and then on a periodic interval (`sweepIntervalMs`, default 60 seconds), alongside `recoverExpired`. Only a document whose body carries the attempt marker is adopted; a same-titled document without the marker cannot be proven ours and is treated as absent.

## Cancellation

- Before a document exists → `cancelled`.
- After a document exists → `cancelled_with_document`, preserving its URL.
- During ambiguous creation → `cancel_pending_reconciliation`; the final cancelled state is chosen only after reconciliation.

## Failure and orphan policy

- Create/body failure without a document → `failed`.
- Body failure after creation → the executor attempts to delete only the document created by this attempt, then passes the cleanup result to `fail`.
- Confirmed deletion → `failed` with no document reference.
- Failed or skipped deletion → `needs_attention`, preserving the document URL and cleanup error.
- Image-only failure → `succeeded_with_warnings`; useful text and successful images remain available.
- A stale queued job without a document → `expired`; a stale queued job with a document → `needs_attention`.

The store never calls Feishu itself. This keeps deletion credentials and API retries in the Bridge executor while making the resulting state transition deterministic and testable. The concrete HTTP endpoints, extension-side `attemptId` storage and Feishu deletion adapter belong to the later Bridge/extension implementation ticket; this ticket defines and tests the state contract they must follow.

## Dual jobs per attempt (#60/#65)

One clip attempt (`attemptId`) may carry two jobs: a `clip` job (the wiki document pipeline above) and a `pdf` job (downloading the page's main PDF and uploading it to Drive). The store keys jobs by `(attemptId, kind)`:

- `submit({ attemptId, kind: 'pdf', pdfSource, title, folderToken })` requires a `pdfSource` (credential-free http(s); the `bytes` variant is described in the credential-fallback section below). `title` is the extension's rendered title, used to name the uploaded file. `folderToken` (#66) is the picker-selected Drive folder; `null` means the Drive root. A failed-job retry takes the latest `folderToken` (the user may have re-selected the folder in the popup). Job files written before #66 have no `folderToken`; pdf jobs are read with `null` (root).
- Idempotent re-submit matches on `(attemptId, kind)`. A `failed` pdf job re-submitted with the same key is reset to `queued` and re-run (`retried: true`) — this backs the popup's 重试 PDF action. Clip jobs keep the old semantics: a terminal clip job re-submitted with the same key is returned unchanged.
- `get(attemptId)` returns all jobs of the attempt (an array, possibly empty); `get(attemptId, kind)` returns the single job or `null`. `claim`/`cancel`/`complete`/`fail` take the kind as a trailing argument (default `clip`).
- Job files written before the dual-job model have no `kind`; they are read as `clip` (read-side migration, storage format unchanged).

The pdf job uses a minimal status set (`queued/awaiting_bytes/running/succeeded/failed/cancelled/expired`) — no `reconciling`, no `needs_attention`, no orphan cleanup. Upload ambiguity (timeout with unknown server outcome) is treated as plain failure: Drive permits same-name files to coexist and orphan uploads are harmless, so the pdf path never reconciles. `complete` for a pdf job requires the uploaded artifact (`{ fileToken, url }`) as its `document`; `fail` always lands on `failed` with stage `pdf` (download and upload are not distinguished). The popup aggregates both jobs of an attempt into a single view (see `describeAttemptView` in `src/extension/popup-state.js`).

### PDF Drive reference backfill (#88)

After a successful Drive upload, the pdf consumer inserts the uploaded PDF into the attempt's clip document as an `@` reference: it looks up the clip job by `attemptId`, and when the clip job has a `document.documentId` it calls `lark.insertDocFileReference({ documentId, fileToken, fileUrl, name })`, which builds a quote-container block (`block_type` 34) holding a text block with a `mention_doc` element (`obj_type` 12 = File, token = Drive file token, `url` URL-encoded) at the document head (`POST /open-apis/docx/v1/documents/{doc}/blocks/{doc}/descendant`, `index: 0` — above the `# Digest` section when present). The File block (`block_type` 23) is unusable here (its token is read-only; it can only be re-uploaded), and lark-cli has no dedicated command, so the call goes through the `api` escape hatch. Insertion runs between the upload and `complete`, so a failure lands as a warning in the pdf job's `result.warnings` — the job still completes `succeeded` and the upload is unaffected.

Idempotency is **mark-before-insert**: the consumer first calls `store.markPdfRefInserted(attemptId)` (no worker guard — the clip job is usually terminal by then), which atomically flips the clip job's `pdfRefInserted` flag and reports `claimed: true` only to the caller that performed the transition; a re-queued duplicate executor (lease expired, `recoverExpired` requeued the job while the old worker was still running) reads `claimed: false` or an already-set flag and skips, so it never double-inserts. If the insert call itself fails, the flag is cleared again (`markPdfRefInserted(attemptId, false)`) and the failure surfaces as a warning — clearing and inserting live in separate error paths, so a flag-write failure is never misreported as an insert failure, and a later retry can backfill the reference. Nothing is inserted when there is no clip job (PDF-tab direct-to-Drive), the clip job ended without a document (terminal failure), or the flag is already set. If the clip job exists but is still in flight (`queued/running/reconciling/cancel_pending_reconciliation`, no `document` yet) when the pdf job finishes, the reference is skipped with the warning “clip 文档尚未建好，PDF 引用未插入” and the flag is left unset — and the **clip side closes the gap (#93)**: after its own document exists, the clip consumer checks the sibling pdf job, and when that job is `succeeded` with an uploaded artifact and the flag is still unset, it backfills the reference through the same mark-before-insert path (filename derived from the pdf job's title/URL by the same `pdfFileName` rules). A backfill failure clears the flag and lands as a clip-side warning; it never fails the clip job.

## Credential fallback and the chunked byte channel (#61/#68)

When the url-type download hits 401/403 (paywalled sources that need the user's cookies), the pdf job does **not** fail — the executor calls `awaitBytes` and the job moves `running → awaiting_bytes`. The popup sees that status while polling and triggers the extension-side feed:

- `POST /v1/jobs` with `pdfSource: { type: 'bytes', url, name, sizeBytes, totalChunks, sha256 }` creates a pdf job directly in `awaiting_bytes`. `url` stays required on the bytes variant: it is both the address the service worker re-fetches with credentials and the idempotency binding key. `totalChunks` must equal `ceil(sizeBytes / 4 MiB)` and `sha256` is the lowercase hex of the whole file; the size ceiling matches the url-type download limit (100 MiB). A url-type job already in `awaiting_bytes` accepts the same submission as a declaration upgrade (`upgraded: true`); the declaration is sticky afterwards — a conflicting `sha256` or `url` is rejected, and only a `failed` job may be re-declared (retry resets to `awaiting_bytes`).
- `GET /v1/jobs/:attemptId/pdf-chunks` returns the received-chunk bitmap (`{ declared, totalChunks, sizeBytes, bitmap }`); `POST` on the same path writes one chunk (`{ index, totalChunks, dataBase64 }`, 4 MiB raw bytes base64-encoded through the existing JSON channel). Chunks land in `staging/<attemptId>.part` (next to the job file) at `index × 4 MiB`; the bitmap lives in a sidecar `.json`. Re-posting a received chunk is idempotent, so a reconnect (the MV3 service worker was killed) just GETs the bitmap and sends only the missing chunks.
- When the bitmap is full, the Bridge verifies the assembled file against the declared size and SHA-256: match → `markBytesReady` moves the job to `queued` and the executor uploads from staging instead of downloading (same lark-cli `drive +upload` path); mismatch → `422 PDF_HASH_MISMATCH`, the job fails, and staging is discarded without ever producing a Drive file.
- Staging lifecycle: discarded when the job reaches a terminal state (executor `finally`) and on hash rejection; the periodic sweep additionally discards staging of jobs expired by TTL and reaps orphaned `.part`/`.json` groups whose mtime exceeds the job TTL. `awaiting_bytes` itself ages out via the job TTL → `expired`, and can be cancelled directly → `cancelled`.
- The clip job's digest stage (#79/#80) can trigger the same fallback: when its own `{{@file}}` attachment download hits 401/403, the clip side moves the pdf job `queued → awaiting_bytes` via `store.requestBytes` (idempotent, terminal states rejected) and then polls — bounded by a 120s budget (executor `digestPdfWaitMs`) with a heartbeat per iteration — until the feed completes and `markBytesReady` returns the job to `queued` with the sticky bytes declaration. Since #91 the pdf lane runs in parallel with the clip lane, so the pdf job may already be `running` (its own download hits the same 401/403 and transitions to `awaiting_bytes` on its own); when `requestBytes` is rejected but the pdf job is `running`/`awaiting_bytes`, the clip enters the same bounded poll instead of degrading immediately. The clip then re-verifies staging against the declaration and reads the same bytes read-only (never discards: the pdf job still consumes staging for the Drive upload). Timeout, a terminal pdf job (`succeeded/failed/cancelled/expired`), or a declared size over the 32 MB attachment limit all abandon the wait and degrade to a text-only digest with a job warning. The extension feeds bytes exactly once — the digest never gets its own channel.
- **In-memory byte sharing (#94)**: a url-type pdf job and the same attempt's `{{@file}}` digest download the same URL, so the pdf lane hands its downloaded bytes to the digest through an in-process map (`executor.pdfShares`, attemptId → deferred) instead of letting the clip download again — one less fetch, and half the exposure to RST-prone hosts like arXiv. The pdf lane resolves the entry after a successful url-type download (only while the clip job exists and is non-terminal — PDF-tab direct-to-Drive never shares), rejects it with a `PDF_SHARE_CREDENTIALS`-coded error when its own download hits 401/403 and it transitions to `awaiting_bytes`, and rejects it with the real error when the download fails outright. The digest side waits for the entry up to a 30s budget (`pdfShareWaitMs`, an independent unref'd timer — never the injected `sleep`): resolved bytes are used directly (timeline records a `pdf_share` stage); a credentials rejection is re-thrown in 401 shape so the digest flows straight into the #80 staging path without re-hitting the paywall; any other rejection or a timeout returns `null` and the digest downloads the URL itself (with the #92 transient retry). Entries never touch disk, and the clip consumer deletes the entry when it reaches a terminal state.

The extension side runs two streaming passes over `fetch(pdfUrl, { credentials: 'include' })`: the first computes the incremental SHA-256 and total size needed for the declaration (no disk, constant memory), the second re-reads the stream and POSTs only the chunks missing from the bitmap. A declaration already in the store lets a resumed feed skip the first pass entirely.

## AI digest stage (#75)

A clip job may carry an optional `digest: { enabled, instruction, provider? }` request (validated on `POST /v1/jobs`: `enabled === true` requires a non-empty `instruction` — no length cap, long system prompts are legitimate; `provider` when present must be a non-empty string of at most 64 chars; pdf-only submissions ignore it). The clip consumer runs a **digest stage after `claim` and before `prepareMarkdown`/document creation**: it calls the user-configured AI API and feeds the result into the markdown through `applyDigest` — either substituted in place of a `{{digest}}` placeholder or prepended as the default `# Digest` / `# RAW content` layout.

AI provider presets (#77): `ai.json` holds a named map `{ providers: { 名字: config } }` — each entry carries `apiType` / `baseUrl` / `model` / `apiKey` plus the optional advanced settings `headers` (custom request headers merged into all three API types), `maxOutputTokens`, and `timeoutMs` (per-request timeout, 5–1800 s; defaults to 180 s because reasoning models also spend time thinking). A legacy single-config file migrates to the `默认` provider on first read; `默认` is editable but cannot be deleted or renamed. Managed via `GET /v1/ai/providers` (sanitized list, `默认` first), `POST /v1/ai/providers` (upsert; `renameFrom` moves the stored key to a new name and deletes the old one), `POST /v1/ai/providers/delete`, and probed via `POST /v1/ai/test` (`name` picks the saved provider, per-field overrides merge on top). The API key is never returned by any endpoint.

Per-preset provider pick (#78): `digest.provider` names the provider to use; absent/empty means the default provider (`默认`, else the first stored one). A dangling reference (provider deleted) degrades exactly like a digest failure but with a distinct warning (`AI provider「name」不存在…`) and never calls the AI.

PDF attachment placeholder `{{@file}}` (#81): when the digest instruction (preset-level or global) contains `{{@file}}`, the bridge attaches this clip's PDF to the digest request as a base64 payload instead of sending text only. Each API type has its own attachment shape — OpenAI Responses: the `input` message content becomes a part list with `{ type: 'input_file', filename, file_data: 'data:application/pdf;base64,…' }` alongside the text part; OpenAI Chat Completions: the user message content becomes a part list with `{ type: 'file', file: { filename, file_data: 'data:application/pdf;base64,…' } }`; Anthropic Messages: the user message content becomes a block list with `{ type: 'document', source: { type: 'base64', media_type: 'application/pdf', data } }`. When no PDF is available (preset has `pdfDrive` off, so nothing is fetched — or detection found none) or the PDF exceeds 32 MB, the digest degrades to plain text input (the placeholder is stripped from the instruction) and the job carries a warning; the clip itself never fails over this. The options page renders an inline hint next to the preset-level instruction box when the instruction contains `{{@file}}` but the preset's `pdfDrive` is off — a hint only, never a save blocker, because the global-instruction layer cannot be statically judged.

- **Caching**: a successful digest is persisted with `recordDigest` into `job.digestText`. Any re-execution of `#execute` (ambiguous-create requeue, lease recovery) reuses the cached text and never calls the AI again.
- **Degradation**: a digest failure never fails the job. It is recorded in the timeline (`{ kind: 'stage', name: 'digest', detail }`), surfaced as a warning (`AI 摘要生成失败：…`) through the same `warnings` channel as image failures (partial success), and `applyDigest` blanks the placeholder or omits the default section entirely.
- The digest stage is a phase inside the clip consumer, not a new job kind: `JOB_KIND` / `JOB_KIND_STRATEGY` / `FAILURE_STAGE` are unchanged.

### Streaming and live progress (#86)

`generateDigest` calls all three API types in **stream mode** (SSE deltas) to feed live progress; `POST /v1/ai/test` stays non-streaming (`stream: false`). Request bodies add `stream: true` (chat-completions also `stream_options: { include_usage: true }`). Stream event shapes per type:

- **OpenAI Responses**: text deltas arrive as `response.output_text.delta` (`data.delta`), reasoning as `response.reasoning_summary_text.delta` (or `response.reasoning_text.delta` on newer SDK event lists). The terminal `response.completed` / `response.incomplete` / `response.failed` event carries the full `response` object — the final digest text and the `incomplete`/`failed` failure semantics (`AI_REQUEST_FAILED` with `incomplete_details.reason`, e.g. `max_output_tokens`) are taken from it via the same extractor as the non-streaming path, so the final text and degradation warnings are byte-identical to non-streaming. If a proxy truncates the event stream without a terminal event, the accumulated text deltas are used instead.
- **OpenAI Chat Completions**: chunks carry `choices[0].delta.content` (text) and `choices[0].delta.reasoning_content` (reasoning, the GLM/DeepSeek convention); the stream ends with a `data: [DONE]` sentinel, and the final chunk carries `usage.completion_tokens` when `include_usage` is honored (proxies that omit it are tolerated — the approximate count stands).
- **Anthropic Messages**: `content_block_delta` events with `delta.type == "text_delta"` (text) or `"thinking_delta"` (reasoning); multiple text blocks are joined with `\n` exactly like the non-streaming extractor; `message_delta` carries `usage.output_tokens`; an `error` event fails the request (`AI_REQUEST_FAILED` with the vendor message).

While streaming, reasoning deltas set progress phase `thinking`, text deltas set `writing`; the token count is a cheap per-delta approximation (CJK 1 char ≈ 1 token, other scripts ≈ 4 chars/token — no tokenizer) and is calibrated to the provider-reported `usage` figure when the stream ends. Progress is **memory-only**: the executor keeps `attemptId → { phase, tokens }` in an in-process map (never persisted — the job store rewrites the whole file, so high-frequency writes are forbidden), and `GET /v1/jobs` / `GET /v1/jobs/:id` merge it into the clip job's view as `digestProgress: { phase: 'thinking' | 'writing', tokens }`. Jobs without an in-flight digest (digest disabled, cache hit, pdf jobs, terminal jobs) have no `digestProgress` field; the entry is deleted when the clip job reaches a terminal state. The timeout (`timeoutMs`) covers the whole stream consumption, and a mid-stream abort maps to `AI_TIMEOUT` — same degradation path as any other digest failure.

## PDF-tab submissions (#67)

When the tab itself is a PDF (the browser's built-in viewer), `POST /v1/jobs` accepts a pdf-only body — `{ attemptId, pdfSource, pdfFolderToken?, title? }` with no `snapshot`/`destination` — and queues exactly one `pdf` job. Detection runs in the extension: a `chrome.scripting` probe reads `document.contentType === 'application/pdf'` (the Zotero signal; zero permission increment over `activeTab` + `scripting`), falling back to a `\.pdf$` suffix test on `tab.url` (ignoring query/hash) only when injection fails. The pdf job's `sourceUrl` is the PDF URL itself, so the popup's same-page recovery (`isJobForPage`) works unchanged. The popup renders a single panel for this page form (no preset chips, no preview, no clip job) and the save button re-submits the same `attemptId` after a failure, reusing the failed-pdf retry semantics above. Credential-carrying PDF URLs are out of scope here (#68): the bytes travel via the Bridge's url-type download, which only fits public URLs.
